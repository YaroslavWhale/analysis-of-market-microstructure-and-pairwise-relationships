# OrderBook — локальный стакан + анализ коинтегрированных пар (фильтр Калмана)

Консольное приложение на C++ с двумя режимами:

* **одиночный инструмент** — держит в памяти актуальную копию стакана Binance и раз в секунду печатает лучшие цены и объёмы;
* **пара инструментов** — одновременно ведёт два стакана, оценивает динамический коэффициент хеджирования фильтром Калмана и печатает полный набор метрик коинтеграции (спред, z-score, half-life, ADF, корреляция, торговый сигнал).

## Описание

Консольное приложение на C++, которое держит в памяти актуальную копию биржевого стакана Binance по выбранному инструменту и раз в секунду печатает лучшие цены и объёмы на покупку и продажу.

Данные берутся из двух источников:

- **REST API Binance** — для получения снапшота стакана и параметров инструмента.
- **WebSocket Binance** — для непрерывного потока изменений стакана в реальном времени.

Цены и объёмы хранятся как целые числа, умноженные на множители, полученные из `tickSize` и `stepSize` конкретного инструмента — это позволяет избежать потерь точности `double`.

---

 ## Как работает

1. **Определение параметров инструмента.**  
   Через `GET /api/v3/exchangeInfo` загружаются `tickSize` (шаг цены) и `stepSize` (шаг объёма). Из них вычисляются множители для перевода цен и объёмов в целочисленный вид.

2. **Запуск WebSocket-потока.**  
   Отдельный поток подключается к `wss://stream.binance.com:9443/ws/<symbol>@depth@100ms` и начинает принимать дельты стакана (`depthUpdate`).

3. **Буферизация событий.**  
   Пока не готов снапшот, все входящие WebSocket-события складываются в буфер.

4. **Загрузка снапшота.**  
   Через `GET /api/v3/depth` получается текущее состояние стакана и `lastUpdateId`.

5. **Синхронизация буфера.**  
   Снапшот инициализирует стакан, после чего буфер сливается по правилам Binance:
   - события с `u <= lastUpdateId` пропускаются;
   - первое валидное событие должно удовлетворять `U <= lastUpdateId + 1 <= u`;
   - при обнаружении разрыва запрашивается новый снапшот.

6. **Live-режим.**  
   После синхронизации каждое WebSocket-событие применяется к стакану сразу. Раз в секунду главный поток печатает лучшие bid/ask.

7. **Автовосстановление.**  
   Если в рантайме возникает разрыв `updateId`, программа сама перезапрашивает снапшот и продолжает работу.

## Анализ коинтегрированных пар (фильтр Калмана)

Если запустить программу с двумя символами (`-sym` и `-sym2`), она превращается
в инструмент анализа зависимости двух коинтегрированных рядов.

### Как это работает

1. По каждому символу открывается свой WebSocket-поток и держится свой стакан
   (`OrderBookCore` хранит несколько книг одновременно).
2. Раз в секунду из каждого стакана берётся middle price `(best_bid + best_ask)/2`
   и подаётся в `PairAnalyzer`.
3. `KalmanFilter2D` — обёртка над шаблоном `KalmanFilter<2>` — рекурсивно
   оценивает динамическую модель

   ```
   log(price1) = alpha + beta * log(price2) + шум
   ```

   где состояние `[alpha, beta]`, наблюдение `z = log(price1)`,
   `H = [1, log(price2)]`. Так оценивается **динамический коэффициент
   хеджирования `beta`** и сдвиг `alpha` (random-walk состояние, шум процесса `Q`,
   шум наблюдения `R`).
4. Из модели считается динамический спред
   `spread = log(price1) - alpha - beta * log(price2)`, его скользящее
   среднее/СКО и **z-score** — рабочая торговая метрика.
5. Дополнительно по скользящему окну считаются статистики коинтеграции:
   **half-life** (период полураспада, AR(1) по спреду), **ADF-статистика**,
   **корреляция лог-доходностей** и диагностика инноваций Калмана — всё, что
   нужно для отбора и мониторинга пары.

### Сигналы

`signal` строится по z-score динамического спреда с гистерезисом
(`-entry` / `-exit`):

| Сигнал | Условие | Действие |
|---|---|---|
| `LONG_SPREAD` | `z <= -entry` | купить ногу 1, продать ногу 2 |
| `SHORT_SPREAD` | `z >= +entry` | продать ногу 1, купить ногу 2 |
| `FLAT` | `|z| <= exit` (или ещё нет сигнала) | вне рынка |

### Важно про ADF и half-life

Динамический спред Калмана по построению средне-возвратный (фильтр подстраивает
`alpha`/`beta`), поэтому тестировать на стационарность сам динамический остаток
некорректно. Поэтому **ADF-статистика и half-life считаются по статическому
(Engle-Granger) остатку**: внутри окна делается обычная OLS-регрессия
`log(price1) = alpha_static + beta_static * log(price2)`, берётся её остаток и по
нему строится ADF-регрессия `Δs_t = c + b·s_{t-1} + e_t` (t-статистика на `b` =
ADF) и half-life `= -ln(2)/ln(1+b)`.

* `beta_static` — «классическая» (Engle-Granger) оценка хеджа по окну;
* `beta` — динамическая оценка Калмана (используется для сигнала).

ADF сравнивается с приблизительным 5%-критическим значением `-2.86`
(модель с константой, длинная выборка).

### CSV

При `-csv <FILE>` в файл пишется строка на каждый сэмпл (после заголовка):

```
samples,price1,price2,alpha,beta,beta_static,alpha_static,eg_residual,spread,
spread_mean,spread_std,zscore,half_life,adf_stat,return_corr,innovation,
innovation_var,signal
```

Это удобно для последующего анализа в Python/R (например, отбор пар по
ADF и half-life).

## Потоки

В программе работают два потока.

Основной поток выполняет всю стартовую логику и главный цикл вывода:

Парсит аргументы командной строки.

Делает rest запрос и вычисляет множители.

Создаёт OrderBook и объект websocket_endpoint — в этот момент порождается фоновый поток.

Регистрирует обработчик сообщений WebSocket.

Даёт команду на подключение к WebSocket.

Ждёт 500 мс, чтобы соединение успело установиться и пошли первые события (они уходят в буфер).

Запрашивает REST-снапшот и делает первичную синхронизацию.

Входит в главный цикл: раз в секунду берёт текущие best bid/ask и выводит их в консоль.

Фоновый поток (WebSocket) создаётся один раз в конструкторе websocket_endpoint и работает всё время жизни программы. Он обслуживает сетевой event loop Asio: устанавливает TLS-соединение, открывает WebSocket, принимает входящие сообщения и для каждого вызывает msg_handler. Пока снапшот не готов — события складываются в буфер, после готовности — сразу применяются к стакану.

Оба потока работают с общими данными, поэтому синхронизируются через мьютексы. Переключение между режимами «буфер» и «live» происходит по снапшоту, а актуальность WebSocket-потока контролируется сверкой updateId последнего применённого события — при обнаружении разрыва программа запрашивает новый снапшот.

### Режим пары

В режиме пары (`-sym` + `-sym2`) на одном и том же `websocket_endpoint`
(то есть на одном фоновом io-потоке) открываются **две** WebSocket-подписки —
по одной на символ. Логика одного символа вынесена в класс `SymbolFeed`
(стакан + буфер обновлений + снапшот + mid price), поэтому главный поток просто
раз в секунду читает обе mid-цены, кормит их в `PairAnalyzer` и печатает снимок
анализа. При потере синхронизации по любому из символов он пере-синхронизируется
независимо.
